**Changes to prioritize**

1. **P1: Enforce project visibility on every collection and aggregate endpoint. Confirmed.** A viewer denied direct access to a private artifact can still see that artifact through `/artifacts`, its run through `/overview`, and its experiment through `/experiments?project_id=...`. The isolated reproduction returned 403 for the direct artifact and 200 with private records for the collection calls. Individual resource authorization examines path parameters, while several collection handlers neither apply membership filtering nor check query parameters. Projects and runs already implement filtering, but it is inconsistent across the API. Introduce shared visibility queries and explicit authorization dependencies. Test every list, detail, aggregate, export, and batch endpoint with two projects and a viewer assigned to only one. Evidence: [overview](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:301), [artifact listing](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:936), [authorization](/home/ty/Repos/spectarr/backend/src/spectarr/auth.py:259).

2. **P1: Release completed upload staging data and add recoverable cleanup. Confirmed.** Completing a resumable upload copies its data into immutable storage but retains the original staging payload. A 24-byte test upload left both a 24-byte object and a separate 24-byte staging file with different inodes. There is no completed-upload cleanup in the inspected backend. Consequently, unique agent uploads can retain roughly twice their source payload size before derivatives, and the backup archives staging too. Remove staging after the artifact and completion state are durably committed. Add an idempotent sweeper for completed and abandoned sessions, with protection for active uploads. Also reconcile unreferenced objects left by rejected uploads. Verify restart safety and unchanged completion responses after cleanup. Evidence: [completion](/home/ty/Repos/spectarr/backend/src/spectarr/platform_api.py:915), [storage ingestion](/home/ty/Repos/spectarr/backend/src/spectarr/storage.py:55), [backup contents](/home/ty/Repos/spectarr/scripts/backup.sh:29).

3. **P1: Make upload recovery work after expiry and interrupted verification. Confirmed.** The agent clears an expired upload ID but retains the same idempotency key. Creating the upload again returns the old expired session. The reproduction observed 410 on expiry, the same session returned as expired on recreation, and 409 on the next chunk. Separately, completion commits `verifying` before hashing and registration. A process interruption can leave that durable state behind, and subsequent requests reject it with 409. A test that persisted this interrupted state confirmed the rejection. Define an explicit recovery transition for expired sessions and lease verification work so it can be reclaimed. Reconcile any artifact already committed before retrying completion. Add tests that interrupt the workflow between each durable transition, then reconnect using the real agent retry behavior. Evidence: [session creation](/home/ty/Repos/spectarr/backend/src/spectarr/platform_api.py:736), [completion](/home/ty/Repos/spectarr/backend/src/spectarr/platform_api.py:915), [state checks](/home/ty/Repos/spectarr/backend/src/spectarr/platform_api.py:1332), [agent retry](/home/ty/Repos/spectarr/services/agent/src/spectarr_agent/service.py:102).

4. **P1: Implement server-side browsing, search, and pagination throughout the dashboard. Confirmed.** `/runs` defaults to 100 records, and the client fetches that endpoint once. Project and experiment filtering, search, counts, and CSV export then operate on that subset. With 102 synthetic runs, the default request returned 100 and the next page returned two. An older project's runs can therefore appear absent even though they remain in storage. The same single-page pattern affects project and job listings. Add project and experiment filters, stable ordering, a pagination contract with continuation information, and server-side search. Make exports explicitly export the complete filtered result. Verify more than 100 runs across several projects and a search matching only an older record. Evidence: [run API](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:715), [dashboard filtering](/home/ty/Repos/spectarr/frontend/src/pages/Runs.tsx:18), [API client](/home/ty/Repos/spectarr/frontend/src/api/client.ts).

5. **P1: Coordinate database and object backups, then verify their relationship. Confirmed verification gap, consistency risk established by code inspection.** The backup script snapshots SQLite and subsequently archives live storage. Deletion or reclamation between those operations can remove an object still referenced by the database snapshot. Archive checksums prove that the archive is intact, not that its contents match the database. The restore gate checks SQL connectivity and storage writability. In an isolated check, removing an artifact object did not cause either the database validator or that health endpoint to fail. Protect snapshot-referenced objects from deletion for the duration of backup, or coordinate a filesystem snapshot and database checkpoint. Verify every required object and bundle member against recorded hashes. During restore rehearsals, disable outbound delivery and processing until verification is complete, because the current script starts the normal runtime against copied credentials and queues. Evidence: [backup ordering](/home/ty/Repos/spectarr/scripts/backup.sh:28), [database-only verification](/home/ty/Repos/spectarr/backend/src/spectarr/backup.py:25), [restore checks](/home/ty/Repos/spectarr/scripts/restore-test.sh:83), [health implementation](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:191).

6. **P1: Promote stable image tags only after all release gates pass. Confirmed workflow ordering.** The image job pushes both the version tag and `latest` before the smoke rehearsal. The smoke job explicitly depends on that image job. A failed rehearsal can therefore leave a failing image available to the documented quick-start command, even when GitHub release publication is prevented. Push an immutable candidate, test its digest, and promote exactly that digest to stable tags after the component, container, and Windows gates succeed. Use release concurrency control to prevent overlapping promotions. The release workflow should also require component tests for the tagged commit, rather than assuming a main-branch CI run covers it. Evidence: [early stable tag publication](/home/ty/Repos/spectarr/.github/workflows/release.yml:81), [later rehearsal](/home/ty/Repos/spectarr/.github/workflows/release.yml:224).

7. **P2: Give read-only spectrum queries read permissions. Confirmed.** The spectrum explorer uses `POST /artifacts/{id}/spectra/query`, while generic authorization treats that POST as a library write. A viewer with membership in the artifact's project received 403 with `Missing required scope: library:write`. Give this endpoint an explicit read authorization dependency and evaluate project access using the operation's semantics. Simply overriding its scope is insufficient if the remaining project check still infers write access from POST. Keep audit classification consistent with the same distinction. Verify the explorer as a viewer and through a library-read API token. Evidence: [method-based scope selection](/home/ty/Repos/spectarr/backend/src/spectarr/auth.py:159), [query endpoint](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:1222).

8. **P2: Align dependency resolution and update the vulnerable multipart dependency. Confirmed pins and advisory.** The tested backend lock resolves FastAPI 0.141.1, HTTPX 0.28.1, and AnyIO 4.14.2. The container constraints instead pin FastAPI 0.115.14, HTTPX 0.27.2, and AnyIO 4.9.0. Both pin Starlette 0.46.2, which falls within the affected range of CVE-2025-54121, a moderate multipart upload denial-of-service issue. The upstream advisory lists 0.47.2 as a patched version. Resolve a mutually compatible, maintained dependency set and use the same production resolution in tests and images. Do not update Starlette alone without checking FastAPI's requirements. Run an advisory scan against the final lock and image. Dependabot's Docker entries also target obsolete component directories and omit the root Dockerfile used by the build. Evidence: [container constraints](/home/ty/Repos/spectarr/constraints.txt), [backend lock](/home/ty/Repos/spectarr/backend/uv.lock), [Dependabot configuration](/home/ty/Repos/spectarr/.github/dependabot.yml:39), [upstream security advisory](https://github.com/Kludex/starlette/security/advisories/GHSA-2c2j-9gv5-cj73).

9. **P2: Move blocking file and database work out of the API event loop. Established by code inspection, production latency not benchmarked.** Async handlers directly hash, copy, import, rebuild manifests, and use synchronous SQLAlchemy sessions. The runtime starts a single Uvicorn worker. Large uploads, directory imports, and library rebuilds can occupy the same event loop needed for health checks and worker heartbeats. Authentication also commits token-use timestamps on every authenticated request, increasing SQLite write traffic during polling. Move long operations into durable jobs or bounded thread execution with explicitly owned database sessions. Throttle last-used timestamp persistence. Profile query counts and repeated project-manifest rebuilding with realistic catalog sizes. Verify health and heartbeat latency while large imports and rebuilds run. Evidence: [upload ingestion](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:1544), [path import](/home/ty/Repos/spectarr/backend/src/spectarr/api.py:1596), [token persistence](/home/ty/Repos/spectarr/backend/src/spectarr/auth.py:147), [runtime](/home/ty/Repos/spectarr/backend/src/spectarr/runtime.py:25). FastAPI documents the difference between directly called blocking utilities and thread-pooled synchronous handlers in its [concurrency documentation](https://fastapi.tiangolo.com/async/).

**Maintenance after these repairs**

- Expand tests around behavior that the current suite misses: the permission matrix, full pagination, process interruption, disk-full failures, backup during reclamation, and missing or corrupt objects. Preserve the existing coverage gate, but prioritize those scenarios over increasing the percentage mechanically. Several frontend interaction checks inspect source text, so they cannot establish that an action completes correctly for a real user.
- Introduce Python linting and incremental type checking in CI. Split the approximately 2,300-line API module and 1,400-line platform API module by domain as relevant fixes land. Avoid a repository-wide rewrite before the behavior is covered.
- Reduce large-download buffering in the dashboard. `downloadArtifact` waits for `response.blob()` before starting the browser download. Investigate authenticated streaming or narrowly scoped expiring download authorization, retaining project access checks and avoiding permanent bearer tokens in URLs.
- Improve operational health reporting with last successful worker activity, oldest queue age, free disk thresholds, last verified backup, and agent heartbeat freshness. Process existence and a writable directory provide only a narrow view of health.
- Document recovery procedures, supported upgrade paths, actual storage layout, and how to perform a restore when the original instance is unavailable. Make the release checklist match the implemented gate ordering.

**Feature ideas, in recommended order**

**Later scope decision:** These were exploratory suggestions, not an agreed roadmap. The user selected batch import, which is implemented and documented in [batch import](batch-import.md). QC comparison and the other proposals remain unapproved. Further features should address demonstrated gaps in Spectarr's core intake, organization, inspection, conversion, and preservation workflows.

| Feature | First useful version | Why it fits |
| --- | --- | --- |
| Integrity and recovery center | Background checksum verification, missing-object inventory, safe orphan cleanup preview, last verified backup status | Builds directly on stored checksums and addresses the product's promise to protect original acquisitions |
| Cross-run QC comparison | Compare TIC/BPC traces and existing QC summaries for selected runs, grouped by instrument and acquisition method | The extractor already records the inputs, so this adds scientific utility without creating another processing engine |
| Batch intake and metadata assignment | Import several files with progress, assign project and experiment once, apply a filename rule with preview, and retry failed items | Reduces repeated work compared with the current single-run browser import |
| Saved searches and useful alerts | Save complete server-side filters, notify on failed processing, an overdue agent, a QC threshold, or low storage | Turns passive browsing into routine operational support after search correctness is fixed |
| Portable project handoff | Export selected sources and derivatives with checksums, conversion provenance, SDRF, and a verifiable manifest | Extends existing SDRF and submission export into reproducible transfer between collaborators |

QC thresholds should initially be user-configured and compared within suitable instruments and methods. A generic automated pass/fail label across unrelated acquisitions would overstate what the current summaries establish.

OIDC or institutional SSO becomes valuable when several groups share a deployment. Object storage and distributed workers become valuable when measured capacity demands them. These should follow the demonstrated correctness repairs and actual deployment requirements. The current single-container and SQLite architecture can remain the default while its I/O, authorization, and recovery boundaries improve.

**Suggested delivery sequence**

Start with focused changes for collection authorization and spectrum reads, dashboard pagination, and upload cleanup and recovery. Follow with coordinated backups and digest-based release promotion. Align dependency resolution before the next release. Then use a realistic load fixture to improve event-loop latency, SQL query counts, and manifest generation. The first product feature I would build afterward is QC comparison, with integrity status developed alongside the maintenance work.
